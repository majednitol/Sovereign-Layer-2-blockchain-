1. Wrong contract addresses — generate_genesis.go hardcodes addresses, while app/wasm.go derives them using types.NewModuleAddress("wasm.constitution"), etc. These must be verified to be exactly identical; otherwise genesis balances/contracts are assigned to different addresses.


2. wasm.go address derivation may not match actual CosmWasm contract addresses — types.NewModuleAddress("wasm.*") uses Cosmos module-address derivation, but CosmWasm instantiated contract addresses are normally generated by the Wasm module. Hardcoding them as module addresses can create identity/address inconsistencies.


3. Treasury/Reserve balances may be credited to the wrong address — If the generated contract address differs from the contractAddrs hardcoded in genesis, the contract will not own the funded tokens.


4. CodeInfo.Creator is inconsistent with contract ownership — Some contracts are created by Constitution, others by Governance. Verify that these creator addresses are intentionally authorized and match the actual contract initialization model.


5. InstantiateDefaultPermission = Everybody conflicts with the comment — The code says governance-only uploads/permissions are enforced, but InstantiateDefaultPermission: Everybody allows anyone to instantiate uploaded code. This may be a serious governance/security configuration issue.


6. CodeUploadAccess = Nobody makes the chain unable to upload new Wasm code through normal governance — If upgrades are expected, this configuration may permanently disable code uploads unless a migration/admin mechanism exists.


7. Genesis chain_id verification ignores the CLI --chain-id value — BuildGenesisDoc() accepts any chainID, but VerifyGenesisFileInvariants() always requires "sovereign-1". Running with another chain ID will generate a file and then fail verification.


8. VerifyGenesisWasmChecksums(env) ignores the --out custom path — If --out /tmp/g.json is used, checksum verification still reads chain/genesis.dev.json or chain/genesis.prod.json.


9. VerifyGenesisWasmChecksums() can silently pass if no matching code IDs exist — It should verify that all required CodeIDs 1–4 are actually present; currently a missing code can go undetected.


10. Checksum format handling is potentially wrong — Cosmos SDK protobuf JSON encoding for bytes is generally base64, but the verifier first tries hex. The fallback works, but the encoding assumption should be explicitly validated.


11. Genesis addresses are not validated using Bech32 decoding — Checking only strings.HasPrefix("cosmos1") and length is insufficient. Invalid addresses can pass validation and cause chain initialization failures.


12. Bridge gnosis_safe_address and circuit_breaker_address are validated as Cosmos addresses only by prefix/length — They should be decoded and validated using sdk.AccAddressFromBech32.


13. Hardcoded contract addresses create a single source-of-truth problem — The same addresses exist in generate_genesis.go, wasm.go, and possibly other files. One change can silently break genesis. Derive addresses programmatically instead of hardcoding them.


14. createGenesisAccount() may be semantically wrong for CosmWasm contracts — A CosmWasm contract account should be represented according to the exact wasmd/Cosmos SDK account type expected by the installed SDK version. BaseAccount may not be the correct account type for all contract initialization paths.


15. Duplicate account insertion is possible — Contract accounts and dev accounts are appended without checking whether the address already exists. Duplicate accounts can cause genesis validation or initialization errors.


16. Duplicate balance insertion is possible — Treasury/Reserve balances are appended without checking existing balances for the same address. This can cause duplicate bank balance entries.


17. OperationalFloat is calculated as a constant and can become negative — If Treasury or Reserve allocations are later increased, the code will still compile but should explicitly reject negative operational float.

18. Invariant 1 does not verify actual bank supply — It only checks constants. It does not confirm that the generated genesis bank supply equals CosmosAllocation.


19. Invariant 6 does not verify actual genesis balances — It checks allocation constants, not the actual balances written into bank.balances.


20. RewardsBucket is never actually funded in bank balances — The code reserves it mathematically but does not show where the 100,000,000 TOKEN is held. If rewards are supposed to be distributed from a specific module/account, that account must be explicitly funded.


21. BscEscrowBalance is only a constant, not verified against the bridge state — The code does not prove that the external BSC LockBox actually contains the claimed 300M TOKEN.


22. large_transfer_threshold and max_unlock_per_block units are unclear — These values must be explicitly verified against the bridge module's expected denomination and decimal precision.


23. EVM/Cosmos denomination architecture is inconsistent — ucsov is the Cosmos native token while aesov is the EVM gas denomination, but the code must ensure the EVM module's actual EvmDenom is configured to "aesov"; the current shown code does not verify the actual x/vm genesis params.


24. The comments claim VM and feemarket invariants, but VerifyInvariants() does not verify them — EnableCreate, AllowUnprotectedTxs, NoBaseFee, ElasticityMultiplier, and EnableHeight are not actually checked.


25. The comments claim ERC-20 native token pair verification, but the invariant does not verify it — The code only checks the constant EVMDenom, not the actual erc20.token_pairs configuration.


26. 0x000...0001 as the native ERC-20 address must be verified against Ethermint/erc20 module expectations — If the module treats this as a reserved/special address differently, the token pair may be invalid or unsafe.


27. contract_owner: "OWNER_MODULE" is hardcoded as a string without verifying SDK enum serialization — Confirm that the installed Cosmos SDK/Ethermint version expects exactly "OWNER_MODULE" in JSON.


28. Genesis module order assumption should not be relied on casually — The comment says auth → bank → … → wasm; verify the actual ModuleManager order in app.go. A wrong order can break account/balance initialization.


29. Production environment validation is incomplete — It validates that addresses are non-placeholder, but does not validate that the production addresses are the correct approved addresses.


30. Dev placeholder addresses can still look valid but are not real Bech32 addresses — cosmos1devgsaddressplaceholderxxxxx is not a valid Bech32 Cosmos address. sdk.AccAddressFromBech32 validation would catch this.


31. The address identity problem is the highest-priority issue — The genesis generator must derive contract addresses using the same exact algorithm/source as the application runtime; otherwise auth.accounts, bank.balances, wasm.contracts, and inter-contract configuration may refer to different identities.
